GraphGenerator 设计文档
1. 模块概述
GraphGenerator 是 RAG Agent 的核心模块，负责将用户意图 映射为可执行任务图（TaskGraph）。
设计理念：
离线、零延迟：使用预设模板映射，无需调用 LLM 动态规划。
可预测、可调试：相同意图组合总是生成相同任务图。
易扩展：新增意图或工具链只需修改配置或添加分支。

6. 使用示例
Python
from content_core.graph_generator import GraphGenerator

generator = GraphGenerator()

# 单意图检索
graph = generator.generate(["retrieve"], "找几篇RAG论文")
# → 节点: hybrid_search → rerank

# 比较意图
graph = generator.generate(["compare"], "LoRA和QLoRA区别", entities=["LoRA","QLoRA"])
# → 节点: 并行 hybrid_search ×2 → rerank ×2 → compare

# 复合意图
graph = generator.generate(["retrieve","summarize"], "总结多模态进展")
# → 节点: hybrid_search → rerank → summarize
7. 扩展指南

1. entities 永远为空，compare 链路永远降级
─────────────────────────────────────────
问题：route() 返回 entities: []，_build_compare 需要 ≥2 个实体才能
走 compare 链，否则降级为 simple_search。实际效果是所有 compare 意图
都不会执行 compare 工具，只是搜一下文档。

方案 A：route() 里用 LLM 兜底时一并提取实体
  在 _llm_fallback 的 prompt 中加入实体提取，JSON 输出增加 entities 字段：
  {
    "tasks": ["compare", "retrieve"],
    "entities": ["LoRA", "QLoRA"],
    "confidence": 0.9
  }
  优点：实体精准，与意图识别一次完成
  缺点：LLM prompt 变复杂，多了一个解析字段

方案 B：task_router.py 加独立的实体抽取（重新实现 _extract_entities）
  在 route() 里加一个轻量级实体抽取步骤，不依赖 LLM：
  - 英文：按句法模式抽（"A vs B"、"A和B的区别"）
  - 中文：按 "和/与/跟" 连接的 2-4 字短语
  优点：零成本，不增加 LLM 调用
  缺点：抽取质量有限，长尾情况不准

方案 C：graph_generator 的 _build_compare 在实体不足时调一次 LLM 做实体识别
  当 len(entities) < 2 且意图包含 compare 时，调 LLM：
  "从问题"X和Y有什么区别"中提取要对比的两个实体，返回 JSON"
  只在这种边缘情况多一次 LLM 调用
  优点：只在需要时调，不影响正常流程
  缺点：多了条件判断，逻辑变复杂

方案 D：直接改 _build_compare，不自作聪明降级
  当 entities < 2 时，把整个 query 作为搜索词，搜出来的结果
  按文档分两组（前一半 vs 后一半）做对比，至少让 compare 跑起来
  优点：简单粗暴，不会静默降级
  缺点：对比质量靠运气，文档天然分成两组没有语义保证


2. _resource_hint 定义了但没人调用
─────────────────────────────────────
问题：task_router.py 第 88 行的 _resource_hint() 能识别 paper/code/kg，
但 route() 没调用它，graph_generator 永远收到 resource_hint="doc"。

方案 A：route() 正常分支调用并返回 resource_hint
  resource_hint = self._resource_hint(query)
  加到 route() 返回值中，chitchat 和正常分支统一字段
  优点：改动最小，立竿见影
  缺点：当前 GraphGenerator 的 TEMPLATES 实际上也没用 resource_hint

方案 B：删除 _resource_hint，消灭死代码
  如果短期内用不到，不如直接删掉，减少维护负担
  优点：干净
  缺点：以后要加得重新写

方案 C：删除 _resource_hint，把资源识别合并到 LLM 兜底的 prompt 中
  在 _llm_fallback 的 JSON 输出里增加 resource_hint 字段
  "resource_hint": "paper" / "code" / "kg" / "doc"
  优点：LLM 识别更准确
  缺点：增加 LLM prompt 复杂度


3. 工具 LLM 调用没有容错
─────────────────────────
问题：compare.py、summarize.py、extract.py、reason.py 直接调 litellm，
没有 try/except，没有重试，没有 timeout。DeepSeek 出错会冒到
GraphExecutor 被 catch 成 "[执行错误]" 字符串，不重试。

方案 A：每个工具内部加 try/except + 重试
  每个 tool 函数自己包 retry 逻辑（参考 task_router 的 _llm_fallback）
  优点：每个工具自治，错误不影响其他工具
  缺点：4 个文件重复代码

方案 B：写一个通用 retry 装饰器
  def llm_retry(func):
      def wrapper(*args, **kwargs):
          for attempt in range(1 + cfg.LLM_RETRY_COUNT):
              try:
                  return func(*args, **kwargs)
              except Exception as e:
                  ...
          return ""
      return wrapper

  然后 @llm_retry 装饰每个工具函数
  优点：不重复代码，改一处全局生效
  缺点：装饰器对调用方透明，错误信息丢失

方案 C：在 GraphExecutor 层统一重试
  修改 graph_executor.py 的 execute()，当工具执行失败时自动重试
  优点：改一处，对所有工具生效
  缺点：重试粒度粗，不知道是工具内部错了还是 LLM 超时

方案 D：直接不管，等到 DeepSeek 真超时了再说
  当前错误会被 catch 成 "[执行错误]" 字符串返回给用户
  优点：不崩，用户能看到错误提示
  缺点：体验差，用户收到一段错误文本而不是答案


4. _build_extract_compare 把同一份结果传给 docs_a 和 docs_b
─────────────────────────────────────────────────────────────
问题：extract+compare 链路的最后一步，compare 的 docs_a 和 docs_b
指向同一个 extract 结果，两个输入一样，对比没有意义。

方案 A：改为调用两次 extract 分别提取两个实体的信息，再对比
  hybrid_search(entity_A) → rerank → extract(target=entity_A)
  hybrid_search(entity_B) → rerank → extract(target=entity_B)
  compare(extract_A, extract_B)
  优点：逻辑正确，两条独立检索链
  缺点：需要 ≥2 个实体，且每个实体要搜一次

方案 B：先 retrieve 再分拆文档对比
  一次 hybrid_search → rerank → 把搜索结果按与实体 A/B 的相关性分两组
  → 每组 extract → compare(extract_A, extract_B)
  优点：只用一次搜索，节省一次 LLM 调用
  缺点：文档分拆逻辑复杂，可能分不干净

方案 C：暂时注释掉 extract+compare 组合，标记为待定
  从 TEMPLATES 里移除此组合，等你想清楚方案再加回来
  优点：不产生错误结果
  缺点：少了一个合法组合，更多请求走 LLM 分解


5. tools/registry.py 没人用
───────────────────────────
问题：tools/registry.py 定义了一个通用注册框架（register + get_descriptions
方法），但实际使用的是 graph_executor.py 里 Dict[str, Callable] 的实现。
tools/registry.py 成为死代码。

方案 A：删除 tools/registry.py
  既然没人用，删了干净
  优点：少维护一个文件
  缺点：无

方案 B：把 graph_executor.py 的 ToolRegistry 改为继承或使用 registry.py
  graph_executor.py 的 ToolRegistry 内部调用 registry.py 的注册逻辑
  优点：代码复用
  缺点：多一层无意义的封装

方案 C：将 tools/registry.py 改为工具描述文档生成器
  利用它提供 get_descriptions() 给 GraphGenerator 生成 prompt（但
  GraphGenerator 已经不走 LLM 了，用不到）
  优点：如果未来 LLM 规划功能回归，可以用上
  缺点：当前场景无用


6. 测试文件过时
───────────────
问题：tests/ 下的 7 个测试文件都是基于旧架构写的：
- route() 之前返回 dict 但测试可能假设了旧接口
- generate() 之前返回 TaskGraph 现在返回 List[TaskGraph]
- executor 的接口也变了
大概率跑不通。

方案 A：全部重写
  用 pytest 重写核心流程测试：
  - test_route_known_combos: 已知意图组合能正确返回
  - test_route_chitchat: 闲聊拦截正常
  - test_route_empty_query: 空查询不崩
  - test_route_llm_trigger: LLM 兜底条件正确
  - test_generate_known: 已知模板返回单图
  - test_generate_undefined: 未定义组合返回多图（mock LLM）
  - test_executor_dag: DAG 执行和占位符解析正确
  优点：全面覆盖，回归有保障
  缺点：工作量较大

方案 B：先删掉过时的测试文件
  在重写之前先把肯定跑不通的删掉，避免误导
  优点：清掉技术债
  缺点：一段时间的测试真空

方案 C：只补测试工具函数的测试
  优先保证 tools/ 目录下每个函数有基本测试
  rerank、compare、summarize 等函数的输入输出验证
  路由层的测试排后
  优点：核心逻辑先覆盖，见效快
  缺点：不全面
